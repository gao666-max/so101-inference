# 20 个坑深度讲解 —— 每个坑背后的知识

## 坑 1：安装完 Anaconda 终端无 (base) 前缀

**现象**：conda 装好了但新终端找不到 conda 命令

**根因**：
conda 通过往 `~/.bashrc` 写入 `# >>> conda initialize >>>` 到 `# <<< conda initialize <<<` 之间的脚本来注册自己。
安装脚本有时候没写进去（你之前手动删过旧 conda 的这段代码），所以终端不认识 conda。

**学到的知识**：
- `.bashrc` 是 bash 的启动脚本，每次打开终端都执行一遍。这是 Linux "开机自启" 的基础机制。
- `conda init` 做的事就是往 `.bashrc` 里写一段代码。`which conda` 可以看到 conda 实际装在哪。
- 所有需要终端自动生效的配置都往 `~/.bashrc` 写（如 `export PATH=...`）

---

## 坑 2：Anaconda 自带 conda 版本太老

**现象**：装完 Anaconda 2025.12-2 后 conda 是 25.11.1，老师要求 26.3.2

**根因**：
Anaconda 发行版的打包时间比你下载时间早几个月。它追求稳定，打包时会"压"一个经过验证的 conda 版本，不会用最新的。

**学到的知识**：
- 发行版 != 最新版。就像 Ubuntu 22.04 不会带最新的 Python 3.13。
- `conda install conda=26.3.2` 可以精确升级 conda 本体（conda 也是一个包，能自己更新自己）

---

## 坑 3：vim 命令不存在

**现象**：敲 `vim` 提示 `command not found`

**根因**：
Ubuntu 桌面版默认不装 vim（它自带的是 nano）。vim 需要手动 `apt install`。

**学到的知识**：
- nano 和 vim 都是终端文本编辑器。nano 新手友好（快捷键列在屏幕底部），vim 效率高但需要学操作模式。
- Ubuntu 桌面版和服务器版的默认预装软件不同。这算"最小安装原则"——不用的不装。

---

## 坑 4：Anaconda 自带 Python 3.13，太新

**现象**：`pip install torch==2.7.1` 找不到匹配的 wheel

**根因**：
Anaconda 2025.12-2 自带的 Python 是 3.13。PyTorch 2.7.1 发布时 Python 3.13 还不存在——它为 3.10~3.12 编译了预编译包（wheel）。所以 pip 找不到 `cp313` 的 torchvision。

**学到的知识**：
- Python 版本号不是越新越好。深度学习框架通常落后 Python 1-2 个大版本。
- wheel 文件名里的 `cp313` 表示"为 Python 3.13 编译的"。如果官方没编译这个版本，你只能从源码编译（非常慢）或者降 Python 版本。
- **conda 能精确控制 Python 版本，而 venv 不能——这是 conda 最大的优势。** venv 只是复制系统已有的 Python，conda 可以自己下载任意版本。

---

## 坑 5：pip 默认装成 PyTorch 2.13.0

**现象**：`pip install torch` 装了 2.13.0 而不是 2.7.1

**根因**：
pip 没写 `==版本号` 时默认拉取 PyPI 上最新稳定版。

**学到的知识**：
- pip 的版本管理：`pip install torch`（最新版）、`pip install torch==2.7.1`（精确版本）、`pip install torch>=2.5,<3.0`（范围约束）
- 深度学习项目的 `requirements.txt` 里**必须写死版本号**，否则三个月后重新装就出兼容问题

---

## 坑 6：torchvision 与 torch 版本不对应

**现象**：`torch 2.7.1` 下装 `torchvision 0.20.1` 失败

**根因**：
PyTorch 生态的三个包（torch / torchvision / torchaudio）版本号严格绑定。2.7.x 的 torch 只能配 0.22.x 的 torchvision。

**学到的知识**：
- 查版本映射表：https://github.com/pytorch/vision#installation（官方 README 里有一个版本对应表）
- 大版本号第二位的差值：torch 2.5 → vision 0.20，torch 2.7 → vision 0.22

---

## 坑 7：venv Python 3.13 装不了 torchvision 0.20.1

**现象**：文档说用 venv，但 venv 继承 Anaconda 的 Python 3.13，装不上

**根因**：
`python3 -m venv ~/torch_env` —— 这个 `python3` 指向 Anaconda 的 Python 3.13。venv 复制的是这个版本的 Python。

**学到的知识**：
- venv 是轻量级"软链接"——它不能改变 Python 二进制版本，只能隔离 pip 包
- conda 是重量级"独立安装"——它能下载指定版本的 Python 二进制文件
- **什么时候用哪个**：只需要隔离 pip 包 → venv。需要换 Python 版本 → conda。

---

## 坑 8：共享文件夹 /mnt/shared 权限不够

**现象**：`ls /mnt/shared/` 提示 `Permission denied`

**根知**：
Linux 的文件权限分为三组：所有者（user）、组（group）、其他人（others）。
这个目录的所有者是 `root`、所属组是 `root`。你（gao）不属于 root 组，所以被"其他人"那组权限管。

**学到的知识**：
- `ls -ld /mnt/shared` 看到的 `drwxr-x---` 中，最后三个 `---` 就是"其他人的权限"——全无。
- `chown root:vboxsf` 把目录的组改成 vboxsf，`chmod 750` 让组内用户可以读+执行。
- **用户组和目录权限是两回事**：你加了 vboxsf 组（`usermod -aG`），但目录的组还没改成 vboxsf。

---

## 坑 9：挂载路径是 /media/sf_Shared 不是 /mnt/shared

**现象**：文档写数据在 `/mnt/shared/`，但你的是 `/media/sf_Shared/`

**根因**：
VirtualBox 共享文件夹的自动挂载规则：**固定分配**挂到 `/mnt/`，**临时分配**挂到 `/media/sf_xxx`。你的设置是临时分配。

**学到的知识**：
- `/mnt/` 是传统 Unix 的"临时手动挂载点"
- `/media/` 是现代 Linux 的"自动挂载点"（U盘、共享文件夹等）
- VirtualBox 的 `sf_` 前缀 = Shared Folder 的缩写

---

## 坑 10：ImportError: DEFAULT_FEATURES

**现象**：所有 LeRobot 命令报 `cannot import name 'DEFAULT_FEATURES' from 'lerobot.utils.constants'`

**根因**：
LeRobot 0.4.3 的 `constants.py` 里漏写了 `DEFAULT_FEATURES` 这个常量定义，但至少有 6 个文件在 import 它。这是上游源码的 bug。

**学到的知识**：
- 看 ImportError 的 traceback：找到第一个抛出异常的文件和行号 → 打开它看为什么
- 修上游 bug 的方法：补丁文件 + import（不直接改原文件，便于还原）
- 这个是开源项目 0.x 版本的典型风险——未经过充分测试

---

## 坑 11：串口显示为 /dev/ttyACM* 而非 /dev/ttyUSB*

**现象**：文档写 `/dev/ttyUSB*`，你的是 `/dev/ttyACM*`

**根因**：
Linux 内核对 USB 串口设备有多个驱动。CH343 芯片同时被 `ch341` 驱动和 `cdc_acm` 驱动支持。内核启动时 USB ACM 抽象驱动先抢到了芯片，所以走了 ACM 命名。

**学到的知识**：
- ttyUSB = USB Serial 驱动直接管理（底层协议）
- ttyACM = USB Abstract Control Model（通用 USB 通信框架）
- 两者功能完全一样，只是内核驱动的选择不同
- 这是典型的"环境差异"——不同机器上同一个硬件可能显示不同的名字

---

## 坑 12：ModuleNotFoundError: scservo_sdk

**现象**：`import scservo_sdk` 报找不到模块

**根因**：
`scservo_sdk` 是飞特舵机的 Python 驱动。它不是 LeRobot 的核心依赖，在 `pyproject.toml` 里被标为可选依赖（`feetech = ["feetech-servo-sdk>=1.0.0,<2.0.0"]`），`pip install -e .` 不会自动装可选依赖。

**学到的知识**：
- Python 包名（PyPI 上的名字）和模块名（`import` 用）可以不同：`feetech-servo-sdk` vs `scservo_sdk`
- 可选依赖（extras）不会自动安装，需要 `pip install .[feetech]` 明确指定
- 为什么分开：不是所有人都有飞特舵机，LeRobot 支持多种电机型号

---

## 坑 13：数据采集时虚拟 USB 串口频繁断连

**现象**：`ConnectionError: Failed to sync read 'Present_Position'`

**根因**：
VirtualBox USB 直通在高负载下不稳定。`lerobot-record` 同时跑摄像头 + 领导臂读 + 从动臂写，三个 USB 设备共享 VirtualBox 的 USB 桥接层带宽。当带宽不够时，串口数据包掉包，舵机不响应 → 程序报错。

**学到的知识**：
- VirtualBox 的 USB 直通是软件模拟的，不是原生 USB 驱动。高并发 I/O 下会丢包
- 实体 Ubuntu 没有这个中间层，USB 是内核原生驱动的，带宽稳定
- 原则：**能用实体机尽量不用虚拟机做硬件 I/O**

---

## 坑 14：pip 安装 lerobot 试图下载 700MB CUDA 包

**现象**：`pip install lerobot` 开始下载 `nvidia-cudnn-cu12`（706MB）

**根因**：
pip 看到 lerobot 依赖 torch，而当前系统里没有 GPU 版 torch → pip 自动解析"需要装 CUDA 版 torch" → CUDA 版 torch 依赖 nvidia-cuda-* 系列包 → 触发 700MB 下载。

这些包在你的 CPU 虚拟机上**完全没用**——你没有 NVIDIA 显卡，不需要 CUDA、cuDNN、cublas。

**学到的知识**：
- `pip install lerobot --no-deps`：只装主包，不管依赖。依赖单独手动装
- 清华镜像源（`-i https://pypi.tuna.tsinghua.edu.cn/simple`）只加速下载，不改内容
- 虚拟机上装 torch："CPU 专用源"（`--index-url https://download.pytorch.org/whl/cpu`）不含 CUDA 库，包体积小 1/4

---

## 坑 15：标定阶段从动臂"转圈"

**现象**：点了 ENTER 后从动臂自己慢慢转一圈

**根因**：
`lerobot-record` 的 `connect()` 里内嵌了一个标定步骤。程序逐个把舵机拉到 0 极限 → 拉到 4095 极限 → 记录范围。看起来就像"转一圈"。

**学到的知识**：
- 标定的本质：记录每个舵机的物理行程范围（MIN/MAX）
- 用之前手动标定的 ID 名（`so101_follower_single`）可以跳过自动标定
- 以后跑数据采集时用已有的标定 ID，就不会转圈了

---

## 坑 16：程序退出后从动臂抖动

**现象**：Ctrl+C 退出后从动臂微微颤动

**根因**：
程序异常退出时，串口通信断了，但舵机还在**通电状态**（Torque_Enable=1）。舵机在试图保持最后一个目标位置，但串口噪声产生微小的指令波动 → 反复"纠偏" → 抖动。

**学到的知识**：
- 每次退出程序后要**从动臂断电再上电**，养成习惯
- 更好的做法：程序退出前显式 `disable_torque()`（我们最后几版脚本加了这个）

---

## 坑 17：服务器端 pip 降级 torch 为 CPU 版

**现象**：`pip install lerobot` 后 `torch.cuda.is_available()` 返回 False

**根因**：
pip 的依赖解析是"找所有包的最大兼容集合"。如果 lerobot 声明依赖 `torch>=2.2.1`，pip 可能选了 CPU 版本的 torch 来满足这个约束。

**学到的知识**：
- 先装 lerobot，再手动 `pip install torch torchvision torchaudio -i 清华源` 重装 CUDA 版 torch
- 清华源上的 torch 包**自带 CUDA 支持**（不需要 `+cu121` 后缀），这是后来的变化

---

## 坑 18：av.option.Option 不兼容

**现象**：`AttributeError: module 'av' has no attribute 'option'`

**根因**：
LeRobot 新版源码里写了 `dict[str, av.option.Option]` 作为类型注解。但服务器上的 av 库编译时 API 变了——这个 `option` 子模块不存在了。类型注解在运行时被读取（因为代码里用了 `from __future__ import annotations`），所以报了 AttributeError。

**学到的知识**：
- Python 类型注解在某些情况下会被运行时解析（如 `get_type_hints()`）
- `sed -i 's/old/new/g'` 是批量替换文件内容的标准命令，`g` = global 替换所有出现
- 这种"源码 bug + 环境差异"是 AI 部署岗的日常

---

## 坑 19：训练脚本参数不兼容

**现象**：`lerobot_train.py: error: unrecognized arguments: --device=cuda`

**根因**：
服务器端通过 `pip install lerobot` 装的是**最新版**，参数体系跟你本地 0.4.3 完全不同。通俗地说：同一辆车，方向盘位置换了。

比如：
- 旧版：`--device=cuda`
- 新版：`--policy.device=cuda`

**学到的知识**：
- 任何 CLI 工具，拿到手第一步跑 `--help` 查看支持的参数
- pip 版和 git 源码版可能参数不兼容
- 处理方式：不要猜参数名，老老实实看 help 输出

---

## 坑 20：浏览器上传数据集损坏

**现象**：JupyterLab 上传 296MB 文件后服务器只有 60MB，解压缩失败

**根因**：
浏览器对超大文件的 HTTP 上传没有断点续传。网络波动导致 TCP 连接在被断开 → 服务器只收到部分数据。

**学到的知识**：
- `split -b 50M` 把大文件切成 50MB 小片，上传后 `cat part_* > original` 合并回来
- 这是 Linux 下大文件传输的经典方案——HTTP/SCP 对 50MB 的文件毫秒级可传完，不会断
- 数据完整性校验：`ls -lh` 看合并后的大小是否等于原始大小
